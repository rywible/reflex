# Preflight Domain residency before breadth sweeps

Repository experiments inspect the Runtime's exact mandatory resident reservation before opening an Improvement Session. The decomposition reports external Verification workers, Runtime and durability stacks, retained Operator state, maximum per-lane Operator scratch, their fixed total, and the remaining dynamic headroom under the registered Resource Envelope. The production Runtime and the inspection share one calculation so diagnostic accounting cannot drift from enforcement.

The Lean public-optimizer harness supports an explicit `preflight` mode. It prepares and kernel-replays the selected Seed and Operator corpora under the same host-isolated supervisor, constructs both training and held-out Domain Definitions, emits the resource decomposition and selected declarations, then stops without training or Candidate Verification. Full Development reports retain the same decomposition. These protocols remain repository-only and do not enlarge the public Reflex or Lean interfaces.

The 16-claim v19 training run already reserved 18.700 GB at peak, including a fixed 16 GiB Lean worker allowance. Extrapolating corpus breadth from aggregate peak alone cannot distinguish the constant verifier cost from library-index and dynamic-search growth. A blind 32- or 64-claim run could therefore be either needlessly rejected or unsafe for the host. Preflight makes the fixed cost and available dynamic headroom observable before the next same-budget breadth treatment; it does not predict dynamic peak or certify that a run will fit.
