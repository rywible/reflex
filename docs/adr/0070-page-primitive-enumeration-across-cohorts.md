# Page Primitive enumeration across Verification Cohorts

The Runtime retains a Primitive Enumeration Cursor for every pending Search Frontier parent and every installed Primitive Operator. A bounded generation transaction resumes each deterministic legal-Application order at its retained offset, materializes one page plus a one-Application lookahead, and advances the cursor only when every materialized Candidate is either retained for later selection or crosses the same durability transaction as its Verification outcome. An Operator is complete only when enumeration ends without filling the lookahead. A parent leaves the pending tail only after every Primitive Operator is complete and its bounded Derived Operator exploration has run.

Pending parents form a restart-complete round-robin queue. Parents whose current page remains incomplete move behind unvisited parents, preventing a broad first group of Seeds from monopolizing generation while later correctness claims receive no Candidate choices. The Domain Bundle Recovery segment records queue order, the exact per-Operator offsets, and whether Derived exploration has run. Recovery rejects duplicate parents, mismatched Operator counts, impossible offsets, completed pending records, and parents absent from the reconstructed Search Frontier. Cursor heap storage is charged as retained resident state and its encoded bytes remain subject to the durable Resource Envelope.

`ApplicationWriter` implements paging without adding a caller or Domain configuration surface. For bounded Runtime use it silently discards the retained prefix, accepts the requested page, and consumes one additional legal Application to distinguish an exact final page from truncation. `OperatorAlgebra::enumerate_legal` must therefore retain a deterministic order for identical inputs under one Semantic Identity. `OperatorAlgebra::apply_batch` must materialize exactly one Candidate per legal Application; cardinality drift is a protocol defect and terminates the Runtime. These requirements make an integer offset sufficient, portable, and independently auditable.

Derived Operators remain bounded accelerators rather than a second exhaustive reachability mechanism. They are sampled once per parent under the pinned Knowledge Revision; when consolidation changes the active Derived Operator set while a resource-exhausted tail survives, the Runtime resets Derived sampling for that tail before sealing the promoted Knowledge Revision. Primitive closure provides the exhaustive resumable path. This avoids persisting domain-specific cursors through a branching Derived program while preserving correctness because every Derived result remains reachable through its Primitive steps and still requires Verification.

## Context

The 32-training-claim Lean breadth treatment stopped after 80 Verification requests with three admitted Artifacts and no promoted Model Revision. It had used only 19.322 GB of its 32 GiB Runtime allowance, 89.2 MB of its 1 GiB durable allowance, and roughly 48 seconds of a ten-minute allowance. The apparent `ResourceEnvelopeExhausted` result came from the first bounded generation slice: the Runtime marked all processed parents complete even when `ApplicationWriter` reported unenumerated alternatives. With 32 parents and nine Primitive Operators, breadth allocation commonly exposed only the first alternative per Operator, so correct proof donors later in Premise Retrieval order were never considered.

Increasing the generation window would be a corpus-specific capacity workaround. It would repeat the earlier heavyweight-Candidate residency failure and still lose alternatives beyond the larger prefix. Inferring progress from Candidate Fates would also be unsound because the Domain contract did not bind an Application cursor to a unique persisted Candidate. Exact Runtime-owned paging fixes the search semantics at their source.

## Consequences

Later pages replay their skipped prefix because the public Domain Definition does not own continuation tokens. This is bounded-memory and portable but can repeat enumeration work; a future optimization may add a semantically equivalent seek hint only after profiling shows prefix replay dominates verified discoveries per CPU-second. Premise Retrieval and other domain indexes remain free to make deterministic enumeration itself efficient.

Runtime revision 15 rejects older bundles rather than interpreting key-only pending state as complete enumeration. Internal Lean Development schemas advance before the breadth treatment is rerun. This record supersedes ADR 0064's claim that one materialized parent window was complete pending work and its conclusion that a resumable cursor was unnecessary.
